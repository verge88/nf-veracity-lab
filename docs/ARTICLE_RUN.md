# Как провести эксперимент для статьи

## 1. Запуск поставляемого стенда с настоящим Open5GS

Нужен Linux или Docker Engine с Linux-контейнерами, доступ к интернету для первой сборки, рекомендуемые не менее 4 vCPU и 8 ГБ RAM, свободное место под исходники и артефакты. Все команды ниже выполняются из корня проекта. Архив поставки находится рядом с каталогом проекта. Версия Open5GS закреплена в Dockerfile как `v2.7.6`; не заменяйте её на `main` посреди серии.

```bash
docker compose build
docker compose up -d --wait
docker compose ps
docker compose exec core cat /opt/open5gs/SOURCE_COMMIT
docker compose exec core python3 -m nf_lab.cli preflight
```

`preflight` должен получить HTTP 200 от реального NRF и через реальный SCP. При ошибке сначала смотрите `docker compose logs core`. Образ и smoke-прогон были успешно проверены 29.09.2026; запись проверки — в `results/open5gs-smoke-20260929`. Если на другой машине сборка падает, зафиксируйте конкретную ошибку/версию, исправьте образ и затем **все** прогоны проводите на одном исправленном образе.

Короткая проверка:

```bash
docker compose exec core python3 -m nf_lab.cli live \
  --scenario falsified-report --out runs/smoke-falsified
docker compose exec core python3 -m nf_lab.cli live \
  --scenario load-spike --out runs/smoke-load
```

Проверьте наличие `completion.json`, `preflight.json`, `events.jsonl`, `windows.jsonl` в каждой папке. В `events.jsonl` должны быть записи `heartbeat`, `observation`, `kie` и `report`; в строках `windows.jsonl` поле `observation_complete` должно быть 1. Для `falsified-report` у целевой NF в окнах атаки ожидается несовпадение наблюдаемого счётчика и самоотчёта. `load-spike` должен оставаться отрицательным контролем. Если нет, результаты статьи начинать нельзя.

Полная серия и выгрузка:

```bash
docker compose exec core python3 scripts/live_matrix.py runs/article-01
docker compose exec core python3 -m pytest -q
docker compose cp core:/opt/open5gs/SOURCE_COMMIT runs/article-01/open5gs-commit.txt
docker compose down
```

`runs/article-01/evaluation` содержит dataset, split, scales, predictions, metrics, ablation, curves, timings и summary. Скрипт запускает 12 независимых повторов каждого из шести сценариев, перемешивая порядок сценариев внутри каждого повтора. Значения в `configs/live.yaml`, `configs/experiment.yaml`, состав Docker-образа и seed сохраняйте вместе с результатами. Для архива статьи дополнительно сохраните `docker compose config`, digest образа, характеристики CPU/RAM/ОС и `schedule.json`.

Разделяйте таблицы `label_attack` и `label_falsification`. Основной результат — разница M4−M3 по F1 на тестовых прогонах вместе с 95% интервалом по целым прогонам. Также публикуйте Recall, FPR, ROC AUC, average precision, время обнаружения с числом пропущенных эпизодов и ошибки на load-spike. Накладной трафик КИЕ в поставке считается на уровне прикладных байтов, это не полная нагрузка на сеть.

## 2. Чтобы вывод относился к штатным AMF/SMF

Описанный выше результат корректно называть «экспериментальные AF через настоящий Open5GS NRF/SCP». Он проверяет механизм и 5G SBA транспорт, но не обнаружение компрометации исходного кода Open5GS AMF/SMF. Для такого вывода нужна отдельная серия:

1. Поднимите полный 5G SA Core (MongoDB, NRF, SCP, AMF, SMF, UPF, AUSF, UDM, UDR, PCF; по потребности NSSF/BSF) по официальному [Quickstart](https://open5gs.org/open5gs/docs/guide/01-quickstart/). NRF и SCP в нынешнем compose не равны полному ядру.
2. Добавьте gNB/UE из [UERANSIM](https://github.com/aligungr/UERANSIM/wiki/Configuration), запишите подписчика в Open5GS. Совместите PLMN, TAC, DNN, S-NSSAI, IMSI/SUPI, K, OPc и адрес AMF NGAP. Проверьте регистрацию UE и создание PDU-сессии до вмешательств.
3. Запустите минимум три сопоставимых экземпляра исследуемой NF с отдельными адресами и контролируемым распределением одинаковой нагрузки. Иначе D_peer смешает разницу роли/нагрузки с атакой.
4. Сделайте независимую точку наблюдения на SCP→producer, запретите прямой обход SCP сетевой политикой, запишите полный HTTP/2 захват до открытия соединений. Импортёр `nf_lab.cli pcap` извлекает сопоставленные запросы и ответы, но ещё не формирует размеченные оконные записи для обучения.
5. Добавьте в исходный код исследуемой NF или в принадлежащий ей sidecar счётчики собственного потока по тем же окнам и API. Это и есть `R_i`; нельзя брать `R_i` из того же сетевого захвата, который считается `O_i`.
6. Реализуйте контрольную процедуру, на которую настоящая NF отвечает проверяемым nonce, и измеряйте КИЕ с независимого агента. Предоставленный `/lab/v1/kie` существует только у экспериментальной Python AF.
7. Вводите вмешательство в исследуемой NF/sidecar: изменение разрешённого поведения, а отдельно — подделку **её** счётчика. Сохраняйте время и цель вмешательства в журнале оркестратора. Не подменяйте журнал наблюдателя. Отдельно измерьте обход SCP, пропуски захвата, общий всплеск и отказ без фальсификации.
8. Постройте адаптер, который объединяет захват, счётчик NF и КИЕ по идентификатору NF и закрытому окну в схему `windows.jsonl`; после проверки полноты применяйте `nf_lab.cli evaluate`. Формула и требования к окнам заданы в [METHOD.md](METHOD.md).

Пункты 3–8 требуют дополнительной реализации под конкретную версию и тип Open5GS NF; готовые патчи AMF/SMF и адаптер из полного PCAP в размеченный датасет в этой поставке отсутствуют. Данные текущей матрицы нельзя переименовать в «эксперимент на компрометированной AMF».

## 3. Формулировка для статьи после первого этапа

«Экспериментальная проверка метода выполнена на управляемых экземплярах AF, зарегистрированных в Open5GS NRF; сервисные обращения и контрольные КИЕ маршрутизировались через Open5GS SCP. Самоотчётность AF формировалась отдельно от независимого наблюдения SBI. Сценарии фальсификации вводились в управляемые экземпляры NF. Эксперимент не включает модификацию штатных AMF/SMF и не проверяет защищённый профиль TLS/OAuth.»

Такое описание даёт проверяемую связь с Open5GS и сохраняет точные границы полученных результатов.
