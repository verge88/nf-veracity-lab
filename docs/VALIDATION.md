# Протокол проверки поставки

Дата: 28.09.2026. Среда: Windows, Python 3.14.0. Точные версии находятся в requirements-tested.txt и manifest.json результатов.

## Выполнено

- 7 pytest-проверок успешно, включая локальный интеграционный прогон HTTP/2.
- Проверены детерминизм симуляции, отрицательная метка load-spike, отсутствие label leakage, непересечение прогонов между train/validation/test, причинность временных признаков, нулевой D_rep при точном совпадении отчёта, обработка пропущенного отчёта и отсутствие достаточных peers.
- На ручном примере проверены F1/FPR/AUC, неопределённость AUC при одном классе и учёт пропущенных эпизодов.
- На пакетной fixture проверены привязка HTTP/2 к TCP stream и исключение повторного ответа.
- На запущенных HTTP/2 серверах проверены Python NRF/SCP protocol fixture, три AF, независимый observer, отчёты, КИЕ, heartbeat и снятие регистрации. Этот fixture не является настоящим Open5GS.
- Выполнен синтетический эксперимент: 72 прогона, 48 окон, 4 NF, 13 824 строки; результаты в results/synthetic-seed731.

## Что показывают синтетические результаты

Добавление блока отчётности M3→M4 дало прирост F1 около 0.244 для задачи attack и 0.662 для задачи falsification. Парные 95% интервалы по прогонам: [0.099; 0.460] и [0.428; 0.891] соответственно.

При этом **КИЕ и peer-признаки в данном генераторе не показывают устойчивого положительного вклада**. Для falsification вариант M4 без временных признаков даже лучше полной M4 примерно на 0.017 F1. Сравнение с D_rep-only также не подтверждает существенного выигрыша полной модели на этой задаче. Эти результаты сохранены без отбора удачных моделей; они показывают необходимость более реалистичной проверки, а не подтверждают полезность всех компонентов метода.

Это ожидаемая ограниченность управляемого генератора: нарушение отчётности в нём задано явно. Цифры нельзя использовать как результаты обнаружения реальной компрометации Open5GS или как доказательство научной новизны.

## Выполнено 29.09.2026 на настоящем Open5GS

- Docker-образ Open5GS v2.7.6 собран из commit `d9d3abdd480be96fac3bc8a997e83446648763ca`.
- NRF и SCP запущены в одном Linux-контейнере. Прямой NRF discovery и маршрут через SCP дали HTTP 200.
- После исправления обязательного `User-Agent` типа AF выполнен сценарий `falsified-report`: 3 управляемые AF, 24 окна × 3 NF = 72 строки, из них 12 окон вмешательства. Во всех 12 целевая NF занизила счётчик самоотчёта.
- Полнота регистрации обычных запросов — 72/72 окон; ошибок КИЕ — 0/72; в журнале 69 heartbeat и 3 deregistration.
- Те же 7 pytest-проверок прошли в Linux-контейнере.
- Первичные файлы, manifest и машинно-читаемая сводка сохранены в `results/open5gs-smoke-20260929`.

Это успешная проверка **реальных NRF/SCP**, но исследуемые AF и их фальсификация реализованы на Python. Один прогон не используется для оценки M0–M4.

## Не выполнено в этой среде

- Полная матрица 72 независимых Open5GS-прогонов и её сравнительные метрики.
- Сопоставление импортера с реальным PCAP: tshark отсутствует; проверена структура parser fixture.
- Эксперимент с настоящими AMF/SMF, UERANSIM, TLS/OAuth и сетевыми политиками против обхода SCP.
- Проверка временных сдвигов, потерь захвата, сообщающихся нарушителей и адаптивного распознавания КИЕ.

Команды для проверки настоящего NRF/SCP приведены в OPEN5GS.md. Успешный preflight и отдельный live-smoke — обязательные первые шаги перед полной матрицей.
